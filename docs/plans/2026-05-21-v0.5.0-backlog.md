## Theme 1 - Underlord capability surface expansion

The plugin currently surfaces Underlord as one skill (`descript-edit`) with one CLI command (`descript agent`). The help-docs in `docs/help-docs/` document a much richer Underlord capability surface that is already reachable via the agent endpoint with the right prompt -

- Translation (multi-language captions, dubbing)

- Lip sync (matches mouth movement to dubbed audio)

- Studio Sound, Eye Contact, Green Screen (audio/video AI effects)

- Avatars (AI-generated speakers)

- Text-to-speech and AI speech

- Quick Design (auto layouts), AI Video Maker

Two ways to surface these:

### Option 1a - Add specialized skills (`descript-translate`, `descript-lipsync`, `descript-avatar`, ...)

Each skill is a thin wrapper around `descript agent --prompt <pre-built template>` plus operation-specific input collection (target language for translate, voice for TTS, etc.).

Pros - Discoverable. Claude routes to the specialized skill based on user intent. Each skill embeds the prompt-writing best practices for that operation.

Cons - Skill bloat. Currently 9 skills; this would push to ~15+. The agent endpoint is one-shot, so each skill is mostly prompt templating.

### Option 1b - Enrich `descript-edit` SKILL.md with worked examples per operation class

Keep one skill. Document each operation class with example prompts (translate this video to German, add lip sync, replace this clip with an AI avatar, etc.). Lean on the existing pointer-first form.

Pros - Maintains the single-skill discipline. Examples lift directly from `docs/help-docs/`. Lower drift risk.

Cons - Less discoverable. Claude must reason that "translate" routes to descript-edit.

### Option 1c - Hybrid - add ONE "descript-creative" skill grouping the AI-tool surface, leave descript-edit for general agent prompting

Splits the surface into "raw agent" (descript-edit) and "AI tools" (descript-creative). Each AI tool gets a section in descript-creative with one example.

## Theme 2 - Test coverage hardening

Items flagged in v0.3.0 followup field report that weren't addressed in v0.3.2 because they were low-priority -

### 2.1 - Audio-publish smoke real validation

`scripts/smoke/concurrency.ts --mode write` is wired up in v0.4.0 but has never run against real Descript for audio publishes. The script defaults to Video at 480p. Need a `--media-type Audio` option and a real test run to validate audio file extension handling (`.mp3` vs `.mp4`).

### 2.2 - High-concurrency mid-stream failure isolation

v0.3.2 tests concurrency=2 with mid-stream failure. Concurrency 5, 7, 10 untested for failure isolation. The runPool implementation is simple, but parameterized tests would lock in the behaviour.

### 2.3 - Skill confirmation pattern testability

Open design question from v0.3.0 followup §4.2. The model-invocable-with-confirmation pattern lives in SKILL.md prose, not in code, so it cannot be exercised by `npm test`. Options - prompt-based eval harness, snapshot tests on SKILL.md content, accept that this is user-observed.

Worth a dedicated ralplan session if test infrastructure is to be built.

## Theme 3 - Resume pattern generalization

v0.4.1 shipped `descript export --resume`. The pattern (read prior report, reconstruct per-item actions, write a new report with schema_version) is reusable.

### 3.1 - `descript download-published --resume`

Equivalent semantics for the read-only download path. Today `--report` reads slugs from a prior export-report.json but doesn't have file-on-disk awareness. A `--resume` flag would skip items where all requested files exist on disk.

Scope - smaller than the export resume because no publish step exists. Mostly reusing exportResume.ts logic but with the `publish` path removed.

### 3.2 - `descript batch --resume`

Equivalent for the bulk pipeline. Bigger lift because batch is more complex (import + agent + publish per item, not just publish + download). The dry-run gate would need to interact with resume.

Operator-only per the v0.3.3 ADR, so risk profile is the same.

## Theme 4 - Descript API surface refresh

The plugin was built against the OpenAPI captured at `docs/help-docs/Descript API.md` on 2026-05-20. Descript ships new API features periodically. A v0.5.0 planning session should -

- Refresh `docs/help-docs/Descript API.md` and `docs/help-docs/Underlord (beta) Your AI co-editor in Descript.md` from the live help center.

- Diff against the current plugin coverage.

- Decide which new endpoints or fields land in v0.5.0.

Likely candidates -

- Status endpoint stability (currently flagged "work in progress" in the OpenAPI).

- New job types (the current `JobType` is `import/project_media | agent | publish` - if Descript adds, say, a publish-batch job type, plugin would need new wiring).

- New media-item shapes for import (audiogram, multi-language).

## Theme 5 - Plugin distribution and ecosystem

The plugin currently ships as a standalone marketplace (`.claude-plugin/marketplace.json`). v0.5.0 could -

### 5.1 - Aggregate into Julian's broader marketplace

If other plugins exist (e.g. for ClickUp, Slack, Stripe per memory entries), aggregate descript-plugin into a unified marketplace.

### 5.2 - Plugin manifest schema validation

The plugin.json validates against the Claude Code plugin manifest schema at runtime. Add a CI/test step that validates the manifest before tagging to catch regressions.

### 5.3 - Versioning automation

The current process bumps `package.json` and `plugin.json` manually + writes CHANGELOG. A `npm version` workflow that updates both files atomically would reduce error surface.

## Themes NOT worth chasing in v0.5.0

Documented here so they aren't accidentally re-added to a future plan -

- **Paragraph-aware transcript endpoint** (original field report §3.3). This is upstream-Descript work, not plugin work. The per-cue Markdown the plugin produces is intentionally denser than Descript's UI export for the chapter-generation use case. Don't re-implement this; the per-cue path is the better default.

- **Re-publishing as a default behavior in --resume**. The v0.4.1 cost-reuse principle (don't republish when slug exists) was the right call. Don't revisit.

- **Adding `disable-model-invocation` to `descript-publish`**. v0.3.3 ADR settled this. The model-invocable + in-skill-confirmation + default-private posture is the chosen pattern. Don't revisit.

- **The Plan-Rename workaround** from the v0.2.1 followup. Resolved by recognizing Underlord handles bulk-metadata operations natively. Don't add it.
